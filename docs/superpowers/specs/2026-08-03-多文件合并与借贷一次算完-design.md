# 方案设计：序时账多文件合并 + 借贷双方一次算完

日期：2026-08-03
项目：往来账龄分析工具
关联需求：docs/requirements/2026-08-03-多文件合并与借贷一次算完-requirement.md

## 一、方案比较

核心设计决策是：方向判断逻辑放哪里。两个方案如下。

### 方案 A（推荐）：新建独立 DirectionResolver 类

新建 src/core/direction_resolver.py，封装三维度判断逻辑。orchestrator 循环里调用它获取方向，再选对应引擎。

**改动清单：**
- 新建 src/core/direction_resolver.py（约 60 行）
- 改 src/core/orchestrator.py（循环里加方向判断，创建两个引擎实例）
- 改 src/gui/step_import.py（多选文件 + 合并）
- 改 src/gui/step_config.py（方向文案改"默认方向"）
- 改 src/core/report.py（账龄汇总表分两个 sheet）
- 改 src/gui/step_result.py（日志输出方向依据、传默认方向参数）

**优点：**
- 方向判断逻辑独立，三维度组合的边界情况容易写单元测试
- 符合项目现有风格（ColumnMapper、DataLoader 都是独立类）
- orchestrator 保持调度职责，不膨胀

**缺点：**
- 多一个文件

### 方案 B：orchestrator 内联模块级函数

不新建文件，把方向判断写成 orchestrator.py 里的模块级函数。

**优点：**
- 不新增文件，改动集中

**缺点：**
- orchestrator 职责变重（调度 + 方向判断）
- 方向判断逻辑的单元测试要和 orchestrator 绑在一起，不好隔离

### 推荐：方案 A

方向判断有三个维度 + 优先级 +关键词匹配，逻辑足够复杂，值得独立成类。独立后测试覆盖各种维度组合更方便。多一个文件的成本远低于测试和维护的收益。

## 二、推荐方案详细设计

### 2.1 DirectionResolver（方向判断器）

职责：输入科目信息，输出方向 + 判断依据。

接口：
- 输入：科目编码、科目名称、该科目期初借方余额合计、期初贷方余额合计、默认方向
- 输出：(direction: str, basis: str)，basis 为 "balance"/"code"/"name"/"default"

判断规则（按优先级降序）：
1. 期初余额方向：借方合计 > 贷方合计 -> 借方；贷方合计 > 借方合计 -> 贷方；相等或都为 0 -> 下一步
2. 科目编码首位：1 -> 借方；2 -> 贷方；其他 -> 下一步
3. 科目名称关键词（长词优先匹配）：
   - 借方类关键词（按长度降序）：其他应收、应收账款、应收、预付账款、预付、待摊费用、待摊、长期待摊
   - 贷方类关键词（按长度降序）：其他应付、应付账款、应付、预收账款、预收、预提费用、预提
   - 名称中先匹配借方关键词，再匹配贷方关键词；匹配到第一个就返回
   - 都匹配不上 -> 下一步
4. 默认方向

### 2.2 多文件合并（step_import.py 改动）

改动点：
1. askopenfilename 改为 askopenfilenames（返回文件名列表）
2. 对每个文件：
   - 读取 Excel
   - 用 ColumnMapper.auto_map 自动匹配列名
   - 校验必要字段（REQUIRED_FIELDS["journal"]）是否全部匹配上
   - 匹配不上的，报错提示文件名和缺失字段
   - 匹配上的，apply_mapping 统一列名
3. 把所有文件的 DataFrame 纵向拼接成一个
4. 预览区显示合并后数据（前 10 行）+ "已合并 N 个文件，共 M 行"
5. 列映射 UI 基于第一个文件展示（和现在一样），后续文件自动处理

数据流：
```
用户选 N 个文件
  -> 逐个读取 + auto_map + 校验必要字段
  -> 逐个 apply_mapping 统一列名
  -> pd.concat 拼接成一个 DataFrame
  -> 保存到 state["journal_df"]
  -> 预览显示合并结果
```

### 2.3 借贷混合计算（orchestrator.py 改动）

改动点：
1. __init__ 不再接收单个 direction，改为接收 default_direction
2. 创建两个引擎实例：debit_engine 和 credit_engine
3. 预先按科目编码汇总期初借方/贷方余额合计（用于方向判断）
4. 循环每个"科目编码 + 明细名称"组合时：
   - 调用 DirectionResolver 判断方向
   - 按方向算期初余额（借方类 = 借 - 贷；贷方类 = 贷 - 借）
   - 选对应引擎实例计算
   - 日志输出方向判断依据
5. 期初分档校验照常生效（用判断出的方向算 opening_balance 后校验）

### 2.4 界面改动

step_config.py：
- "余额方向"卡片的标题改为"默认方向"
- 单选按钮文案改为"借方（应收/预付/其他应收）"和"贷方（应付/预收/其他应付）"
- 加一行小字说明："系统会自动判断每个科目的方向，识别不了的才用这里选的默认方向"

step_result.py：
- _run_calculation 里把 direction 改为 default_direction 传给 orchestrator
- 日志输出增加每个科目的方向判断依据
- 导出时 config 里 direction 改为 default_direction

### 2.5 报告分 sheet（report.py 改动）

改动点：
1. generate 方法里，账龄汇总表从 1 个 sheet 变成 2 个：
   - "借方账龄汇总表"：只含 direction="debit" 的结果，独立合计行
   - "贷方账龄汇总表"：只含 direction="credit" 的结果，独立合计行
2. _build_summary 方法改为接收已按方向过滤的 results 子集
3. _patch_summary_formulas 对两个 sheet 分别补合计公式
4. 其他 sheet（逐笔追溯明细、期初余额验证、期末余额验证）加一列"方向"标注，不分 sheet
5. 参数说明 sheet 的"余额方向"改为"默认方向"

Sheet 结构从 5 个变为 6 个：
1. 借方账龄汇总表
2. 贷方账龄汇总表
3. 逐笔追溯明细（加方向列）
4. 期初余额验证（加方向列）
5. 期末余额验证（已有方向列，无需改）
6. 参数说明

## 三、错误处理

| 场景 | 处理 |
|---|---|
| 多文件某文件必要字段匹配不上 | 报错提示"文件 XXX 的 YYY 列未找到，请检查列名"，终止合并 |
| 方向判断三维度都失败 | 用默认方向，日志标注"默认" |
| 期初分档合计与余额不一致 | 报错（已有逻辑，两个方向都生效） |
| 某方向无科目 | 对应 sheet 为空表（只有表头），不报错 |
| 多文件行数为 0 | 提示"合并后无数据" |

## 五、迁移与回滚

- **兼容性**：老用户选默认方向 = 借方，数据只有借方科目时，方向判断全部走第一优先（余额方向）或第二优先（编码首位），结果与改造前一致。
- **回滚**：如果出问题，DirectionResolver 的判断结果可以全部强制返回默认方向，等效于改造前的单方向模式。无需删除代码，只需在 DirectionResolver 里加一个开关即可回滚。

## 六、ADR 记录

### ADR-0001：方向判断粒度为科目编码级

**决策**：方向判断按科目编码级，同一科目编码下所有明细共用同一个方向。

**理由**：审计实务中科目方向通常以科目编码为单位。明细级方向判断会让同一科目下不同明细用不同引擎，增加复杂度且实务上少见。个别明细反挂作为负余额单列展示已足够。

**代价**：同一科目下个别明细反挂会被"吞"进科目净额方向，但该明细余额仍会作为负余额在报告中单列展示，不影响可见性。

### ADR-0002：方向判断三维度优先级为余额 > 编码 > 名称 > 默认

**决策**：第一优先期初余额方向，第二科目编码首位，第三科目名称关键词，兜底默认方向。

**理由**：期初余额方向是最直接的业务信号（数据挂在哪一列），能自动识别反挂。科目编码首位是标准化信号，覆盖标准编码。科目名称关键词作为第三道防线，覆盖非标准编码。默认方向兜底处理极端情况。
