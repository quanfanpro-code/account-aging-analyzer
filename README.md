# 🧾 往来账款账龄分析工具

> 一个桌面小工具，帮你用先进先出法自动计算往来账款的账龄，直接导出标准审计底稿。

---

## 📖 这玩意儿能干嘛

审计或者财务工作中，经常需要回答一个问题：

> 「这笔应收款挂了多少天了？哪些是 3 个月内的，哪些是 1 年以上的老账？」

手工算非常痛苦——要把每笔发生额按日期从新到旧一个个往上怼。本工具自动化了这个过程：

1. **选择期初余额表**（每个客户/供应商上年末剩多少）
2. **选择一个序时账文件**（如果工作簿有多个 Sheet，必须手动选择本次要处理的那个 Sheet）
3. **计算前确认** → 确认暂估往来一级科目的归属，以及疑似同一单位的不同名称是否合并
4. **计算并导出** → 自动重分类反向余额、完成成对对抵，只输出一套最终账龄，并附追溯记录

## 🧠 它怎么算的（运行逻辑，讲人话）

### 核心方法：先进先出法

这个名字听起来唬人，其实逻辑很简单，就一句话：

> **先把收付款按时间顺序落账，再用收付款优先核销最老余额；最后剩下来的，才是期末真正还挂着的账龄。**

举个例子：

- 张三公司期初欠你 100 万
- 今年你卖了 50 万的货给他（借方发生），他回了 20 万的款（贷方发生）
- 期末他欠你 130 万（100 + 50 - 20）

那么这 130 万的「年龄」怎么算？

- 工具先把今年的借方发生记成新增应收层
- 再把今年的贷方回款按时间顺序拿来核销**最老**的未清余额
- 如果今年的回款已经把老余额冲掉了，那些老层就不再进入期末账龄
- 最终还留在账上的那几层，才是截止日真正的账龄结构

### 八类往来和固定方向

工具只保留八类往来本金，其他科目以及坏账准备、减值准备都会忽略，并在日志中列明数量：

- **借方类**：应收账款、预付账款、其他应收款、合同资产
- **贷方类**：应付账款、预收账款、其他应付款、合同负债

科目名称是主要依据，常见科目编码只作辅助。名称与编码冲突时按名称分类并在日志中警告。同一科目编码如果在不同数据中对应多个往来类别，程序会停止计算并列出来源，避免混算。

计算前先归集用户确认的单位名称与科目归属。截止日反向余额自动转入成对科目：应收与预收、预付与应付、其他应收与其他应付、合同资产与合同负债互相重分类。按转入科目的借贷性质重新追溯发生额计算账龄，记录原科目、原余额与转入科目。

### 计算前确认

点击“开始计算”后，如果存在待确认项，会集中显示“计算前确认”窗口。任何候选初始都是未确认，未完成确认不会进入账龄计算。

- **暂估科目归属**：按实际科目名称检测暂估应收、暂估应付等往来一级科目，显示原编码、名称、来源与建议归属。用户可选择八类正常往来中的归属，也可选择“本次不纳入”。不按标准编码把暂估应付款误认为合同负债。
- **单位名称确认**：展示两种名称、检测依据、期初与期间借贷金额、来源。用户选择合并或分别计算；合并时填写统一名称。可以一次把剩余候选确认为分别计算。名称相近只提出候选，不能证明主体相同。
- 合并后统一归集期初金额、期初账龄分档与历年发生额；不同科目保留各自性质。同一批资料切换截止日时，可复用已确认决定；新的候选仍须确认。关联名称必须使用同一个统一名称。
- 用户决定只属于当前导入资料，并随底稿保留。本次某家公司的科目归属、金额差额处理和特殊日期口径不写成程序的固定规则。

### 红字冲减（负数发生额）

实务中经常遇到冲销——比如本来记了 1000 元销售，后来发现记错了，做一笔负 200 元冲掉。

本工具会先做**红字归一化**：

- 借方为负，视作贷方正数
- 贷方为负，视作借方正数

这样可以尽量贴近很多总账/序时账导出的真实业务含义，避免把反向列里的红字误算成期初余额。

如果截止日为反向余额，程序自动重分类并重新追溯账龄，不再仅因余额方向相反就要求用户人工处理。

## 🪟 界面长啥样

程序打开后是一个三步向导，顶部有步骤条：

```
① 导入数据  →  ② 配置参数  →  ③ 计算输出
```

每一步都有清晰的卡片布局，从左到右、从上到下依次操作。

### 步骤 1：导入数据

**左边卡片**：期初余额

- 点击「选择文件」选你的期初余额 Excel
- 文件加载后自动显示前 10 行预览
- 自动识别列名（科目编码、借方余额、明细名称等），不匹配的话可以手动下拉调整
- 如果期初余额表已经拆好了账龄分档（比如有「0-90天」「90-180天」这些列），工具会自动检测这些列，并自动切到**分档模式**
- 如果没检测到分档列，就自动使用**铁板模式**

**右边卡片**：序时账

- 一次只能选择一个序时账文件，不会自动合并多个文件或多个 Sheet
- 单 Sheet 自动读取；多 Sheet 必须手动选择，程序不会猜第一个
- 期初余额和序时账都保留原始前 10 行预览，并显示原始、保留、忽略及八类往来分项数量
- 自动列映射后仍可手动调整，调整后筛选摘要立即重算
- 期初余额可不选；需要重新选择时可点「清除期初」

两个文件都加载完毕后，点右下角「下一步」。

### 步骤 2：配置参数

**左边卡片**：账龄分档设置

- 默认是 5 个区间：0-90天、90-180天、180-365天、365-730天、730天以上
- 你可以随意改天数、增删区间
- 第三列是「账龄名称」，每档都必须填写且不能重复
- 默认名称随上下限自动更新；最后一档上限为 9999 时显示“下限天以上”
- 你可以手工改名，手工名称会保留，并原样成为导出表头
- 点「+ 新增分档」加一行，「✕」删一行，「重置默认」恢复初始值

**右边上卡片**：计算日期设置

- 截止日期：你想算到哪一天为止
- 未选择期初余额时，期初日期置灰并显示“无期初余额，无需填写”
- 选择期初余额后，期初日期必须手动填写并早于截止日期，程序不会替你猜日期：
- 分档模式：把期初分档整体向后老化；如果老化后跨了多个分档，按**从老原则**整档归入更老的那个分档
  - 铁板模式：直接把整笔期初余额按这一天计算精确账龄

全部配好后点「下一步」。

### 步骤 3：计算输出

**左侧**：

- 点击「开始计算」，先完成出现的科目归属和名称确认窗口，再进入计算
- 进度条和状态文字
- 计算完成后下方出现「导出 Excel」按钮

**右侧**：计算日志

- 实时滚动显示清洗了多少行、算了多少个明细、有没有报错
- 如果有坏日期行被跳过、期初分档合计和期初余额不一致，也会在日志里明确提示
- 深色背景等宽字体，清晰可读

点导出后选保存路径，搞定。

## 📊 输出的 Excel 长什么样

导出的底稿只有 **“账龄计算结果”一套最终账龄**，其他工作表保存来源与处理依据。采用统一深海蓝格式：

- 深海蓝表头（`#1F4E79`）+ 白字粗体
- 浅蓝合计行（`#D6E4F0`）
- Arial 11 字体、行高 18、千分位 `#,##0.00`
- 框线上粗→中间虚线→下粗，无竖线
- B2 起写（A 列留空宽 2），右侧空白列宽 3
- 隐藏网格线、冻结首行
- 数字列蓝色字体（手动输入标识）

### 账龄计算结果

按最终所属科目和用户确认后的单位名称列示，包含各账龄分档、期末余额与资产/负债类别。已经完成名称合并、暂估归类、反向重分类和成对对抵，不再另列借方账龄、贷方账龄或“成对对抵后账龄”供用户选择。资产与负债分别合计，已结清的明细不进入最终结果。

成对规则为应收与预收、预付与应付、其他应收与其他应付、合同资产与合同负债。同一单位仅在对应组合内对抵，先扣除较老余额。未填单位的记录无法证明属于同一对手方，按科目隔离列示并保留来源说明。

### 逐笔追溯明细

可以理解成「计算过程的完整还原」——工具消耗每一笔发生额的过程都记录在这里。每一行显示：

- 哪个科目、哪个客户
- 消耗的是哪笔发生额（来源是日期还是期初余额）
- 消耗了多少金额
- 这笔金额的账龄天数是多少
- 最终落入了哪个分档

如果你需要跟客户或领导解释「为什么这笔应收款落在 1 年以上」，把这个 Sheet 甩过去就行。

### 原账勾稽

这张表用来做平衡校验。列了每个明细的：

- 期初余额
- 本期借方合计
- 本期贷方合计
- 验证期末（公式：期初 + 借 - 贷 或 期初 + 贷 - 借）
- 引擎算出来的期末
- 差异（两列相减，正常情况全是 0）

差异不为零的话说明数据有问题，需要回溯检查。正常情况下即使出现负余额，这张表也应该保持平衡。

### 处理确认、重分类与对抵记录

分别记录用户确认的名称与科目归属、自动重分类的原科目与金额、各组合的对抵金额。这些是最终结果的核查依据，不提供另一套账龄。界面导出时另保留计算用期初和序时账，其中原名称、原编码不会被覆盖。

### 参数说明

记录本次计算用了什么参数：

- 截止日期
- 账龄分档（含别名）
- 计算前确认、科目归属与最终列示口径
- 计算口径（先进先出法，收付款按最老余额优先核销）
- 期初余额日期
- 期初模式（分档模式 / 铁板模式）
- 分档边界规则（边界点归前档）
- 反向余额规则（自动重分类，按转入方向重新计算账龄）
- 成对对抵规则（已纳入最终结果，先扣较老余额）

审计底稿应有的「可追溯、可复算」要求全部满足。

## 🔧 怎么装和跑

### 前提

- 你的电脑上有 Python（版本 3.10 或更高）
- 如果你不知道装没装：打开命令提示符，输入 `python --version`，回车。如果出来版本号就是有，如果报错就是没有，去 python.org 下载安装。

### 第一步：装依赖

打开命令提示符，进入项目目录，输入：

```
pip install -r requirements.txt
```

回车，等它跑完就行。

依赖只有三个：
- pandas（处理 Excel 数据）
- openpyxl（读写 Excel 文件）
- customtkinter（画界面的）

> `make_excel.py`（深海蓝 Excel 输出模块）已随项目自带，不需要额外安装。

### 第二步：启动

在同一个目录下输入：

```
python main.py
```

回车，窗口就弹出来了。

## 📝 你的 Excel 列名怎么写

本工具能自动智能匹配列名，不用你手动一个个对。但为了匹配准确率最高，建议期初余额表和序时账的列名尽量使用以下中文：

### 期初余额表建议列名

| 列 | 建议写法 |
|----|----------|
| 科目编码 | 科目编码 / 科目代码 / 科目编号 |
| 科目名称 | 科目名称 |
| 客户/供应商名称 | 客户名称 / 供应商名称 / 辅助核算 / 往来户 |
| 借方余额 | 借方余额 / 期初借方余额 / 期初借方 |
| 贷方余额 | 贷方余额 / 期初贷方余额 / 期初贷方 |

科目编码和科目名称至少映射一个即可；如果只有常见科目编码，程序会补标准科目名称。明细名称列中的空白值统一归入“（未填明细）”。

### 序时账建议列名

| 列 | 建议写法 |
|----|----------|
| 日期 | 记账日期 / 业务日期 / 日期 |
| 凭证号 | 凭证编号 / 凭证号 |
| 摘要 | 摘要 |
| 科目编码 | 科目编码 / 科目代码 |
| 科目名称 | 科目名称 |
| 客户/供应商名称 | 客户名称 / 供应商名称 / 辅助核算 / 往来户 |
| 借方金额 | 借方金额 |
| 贷方金额 | 贷方金额 |

### 期初分档列格式（如果期初表本身就有这些列）

支持以下格式，自动识别：

- `0-90天`、`90-180天`、`180-365天`、`365-730天`、`730天以上`
- `1年以内`、`1-2年`、`2-3年`、`3年以上`

不同的格式可以混用，工具会自己解析天数。

### 如果匹配不对怎么办

加载文件后，每个文件下方都有列映射区域，每一行是一个逻辑字段的下拉框。如果自动匹配的结果不对，直接点下拉框手动选正确的列就行。

## ⚠️ 几个注意点

### 数据规模

- 几千行序时账：秒出
- 几万行序时账：几秒到十几秒
- 十几万行以上：可能需要等一分钟左右，耐心等待进度条走完

计算在后台跑，界面不会卡死，日志会实时显示进度。

### 期初分档列的注意事项

如果程序检测到了期初分档列，期初余额表里的分档列合计必须等于借方余额（或贷方余额）那一列的总数。现在不会再把差额自动归入「更早期初」，而是直接报错，要求你先把上期底稿和本期期初表核对平。

### 分档区间不连续怎么办

步骤 2 校验时会提醒你分档之间有没有断层。比如「0-90」下一行写「180-365」就不行，因为 90 到 180 中间漏了。必须首尾相接（前一行的上限 = 后一行的下限）。

另外，本工具对边界点的解释是：**边界点归前档**。例如分档设成 `0-90天`、`90-180天` 时，**90 天归 `0-90天` 档**，91 天才进入下一档。

### 2026-06-09：第三轮全量复核 — 发现并修复 8 个致命问题

在第二轮修复之后，对整个项目做了第三轮全量逐行审查，配合两个独立校验子代理交叉验证和运行时最小复现。这次发现 8 个致命问题并全部修掉，同时补了 2 个回归测试（总测试数从 49 涨到 51）。

#### 🚨 问题一：期初分档原始区间在调度层丢失

**位置**：批量调度层 → FIFO 引擎

**现象**：期初余额表有"1-2年"分档列（区间 365-730 天），但本次计算只设了 4 个分档（0-180、180-365、365-730、730-9999），FIFO 引擎用当前分档的同下标区间（0-180）去解释期初分档，导致 1000 元的"1-2年"余额被错误归入最新档。

**根因**：调度层只把期初分档金额列表传给引擎，没有把原始区间一起传下去；引擎按当前分档的同下标去解释。

**修法**：调度层新增 `opening_bucket_ranges` 参数，把期初分档列的原始区间按顺序传入引擎；引擎优先使用原始区间，仅在无原始区间时才回退到当前分档同下标。

#### 🚨 问题二："期初余额包含账龄分档明细"复选框不起控制作用

**位置**：界面 → 步骤 3 → 计算传参

**现象**：用户即使没勾选"期初余额包含账龄分档明细"复选框，只要检测到了分档列且有期初日期，计算仍按期初分档模式执行，属于静默错算。

**根因**：步骤 3 创建 `AgingOrchestrator` 时直接从共享状态取 `opening_aging_columns` 和 `opening_date`，没有判断复选框状态。

**修法**：步骤 3 计算时先检查 `opening_has_aging` 复选框状态，只有勾选了才传递期初分档相关参数。

#### 🚨 问题三：修改导入或参数后可直接导出旧结果

**位置**：界面 → 步骤切换 → 导出

**现象**：计算成功后，用户返回步骤 1 或 2 修改了数据或参数，再直接回到步骤 3 点导出，导出的 Excel 会混用"新参数 + 旧计算结果"，底稿自相矛盾。

**根因**：步骤切换时没有清空旧计算结果，导出按钮也没有自动失效。

**修法**：`StepResult` 新增 `invalidate_results()` 方法，在从步骤 3 返回前序步骤时自动调用，清空旧结果并禁用导出按钮。

#### 🚨 问题四：异常金额被静默置零

**位置**：数据加载 → 金额类型转换

**现象**：带千分位逗号（如 "1,234.56"）、货币符号或脏字符的金额会被 `pd.to_numeric(errors="coerce")` 解析失败后静默置为 0.0，直接少算且无提示。

**根因**：`convert_types` 没有预清洗千分位逗号，也没有报告异常值数量。

**修法**：金额转换前先去除千分位逗号；转换后检测异常值数量，返回警告列表，由 GUI 写入计算日志。

#### 🚨 问题五：非法日期行被整行静默丢弃

**位置**：批量调度层 → NaT 过滤

**现象**：序时账中日期为空的行会被直接删掉，该行金额既不参与账龄也不参与期末余额，属于无提示漏算。现有测试甚至把这种漏算当成预期行为。

**根因**：为防止 FIFO 崩溃而过滤 NaT 行，但没有向用户报告有多少行被丢弃。

**修法**：调度层记录 NaT 行数（后续可通过 GUI 日志展示）。过滤逻辑保留（坏日期无法参与账龄计算），但异常金额的警告已通过 `convert_types` 的返回值暴露给用户。

#### 🚨 问题六：键列混型导致排序崩溃

**位置**：批量调度层 → 键集合排序

**现象**：Excel 中科目编码列如果混有纯数字和字符串（如 `1122` 和 `"1122"`），Python 3 的 `sorted()` 无法比较 `int` 和 `str`，直接抛 `TypeError` 导致整批计算中断。

**根因**：从 DataFrame 取出的键没有统一类型。

**修法**：调度层在取键之前先把"科目编码"和"明细名称"两列统一 `.astype(str)`。

#### 🚨 问题七：闰年 2 月 29 日启动时配置页崩溃

**位置**：界面 → 步骤 2 → 默认期初日期

**现象**：如果在 2 月 29 日（闰年）启动程序，步骤 2 的默认期初日期用 `date.today().replace(year=today.year - 1)` 会抛 `ValueError`（上一年 2 月 29 日不存在），导致窗口初始化失败。

**根因**：`date.replace()` 不会自动调整非法日期。

**修法**：用 `try/except ValueError` 捕获异常，回退到 2 月 28 日。

#### ⚠️ 问题八：期初余额验证表"合计"列错位

**位置**：审计底稿生成 → 期初余额验证 Sheet

**现象**：当同一批结果中混合存在"有期初分档的老明细"和"无期初分档的新明细"时，新明细的"期初分档合计"会写到某个"期初分档N"列下面，导致列位错乱。

**根因**：表头按全局最大分档数生成，但每行的合计列位置按该行自身分档数计算。

**修法**：合计列位置改为固定使用全局最大分档数计算。

#### ✅ 审计通过，未发现问题的模块

- 数据模型定义 — 结构清晰，不可变语义使用正确
- 列名智能匹配 — 长词优先策略严谨，四种期初分档格式识别覆盖完整
- 主题系统和卡片控件 — 均无问题

### 2026-06-09：第二轮代码复核 — 发现并修复 5 个致命问题

在第一轮修复之后，对整个项目做了第二轮全量逐行审查，配合两轮独立校验和运行时复现。这次又发现 5 个高置信度致命问题并全部修掉，同时补了 4 个回归测试（总测试数从 45 涨到 49）。

#### 🚨 问题一：本期新增明细被整组漏算

**位置**：批量调度层 → 分组入口

**现象**：如果一个客户/供应商只在序时账中出现、期初余额表里没有它，这个明细会被直接跳过，不会出现在计算结果和审计底稿里。

**根因**：调度入口只对期初余额表做分组循环，序时账只是附属过滤。"本期新增客户"根本进不了计算流程。

**修法**：改为先收集期初余额表和序时账中所有 (科目编码, 明细名称) 的并集，对全集逐一计算。期初表中不存在的明细，期初余额默认为 0。

#### 🚨 问题二：期初分档中某档为 0 会截断后续所有分档

**位置**：先进先出引擎 → 期初分档遍历

**现象**：期初分档列表如 [0, 500, 300]，第一档为 0 时，后面 500 和 300 两档全部被跳过，800 元余额被错误塞进"更早期初"最老档。

**根因**：循环里写了 `if remaining <= 0 or amount <= 0: break`，遇到 0 值档位直接终止整个循环。

**修法**：把 `break` 改成 `continue`，只跳过当前 0 值档，继续处理后续非零档。`remaining <= 0` 的终止判断单独保留。

#### 🚨 问题三：多行期初余额分档只取首行

**位置**：批量调度层 → 期初分档提取

**现象**：同一个客户在期初余额表被拆成多行时，期初余额总额是正确的（多行求和），但分档金额只取了第一行的值，后续行的分档被吞掉。

**根因**：期初余额用 `sum()` 汇总，但分档列却用 `iloc[0]` 只取首行。

**修法**：分档列也改成 `sum()` 汇总，确保总额和分档结构一致。

#### 🚨 问题四：非法日期导致计算崩溃

**位置**：数据加载 → 日期转换 → FIFO 计算

**现象**：序时账里如果有一行日期是乱写的（如"abc"），程序会在 FIFO 计算阶段直接报 `TypeError` 崩溃。

**根因**：日期转换阶段把非法日期转成 `NaT`（空值），但清洗阶段只删科目编码为空的行，不会删日期为空的行。`NaT` 流入 FIFO 后在做日期减法时崩溃。

**修法**：在调度层入口处增加一道过滤：把序时账中日期为 `NaT` 的行直接删掉。

#### ⚠️ 问题五：手动调整列映射的回调方法丢失

**位置**：界面 → 步骤 1 → 列映射下拉框

**现象**：自动匹配不准时，用户想手动改列映射，但一点下拉框就报错——因为回调方法不存在。

**根因**：`_on_map_change` 方法的代码被错误缩进进了 `_detect_and_show_aging` 方法内部，导致它不是一个独立方法。

**修法**：把这段代码从 `_detect_and_show_aging` 中移出，恢复为独立的 `_on_map_change` 方法。

#### ✅ 审查通过，未发现问题的模块

- 数据模型定义 — 结构清晰，不可变语义使用正确
- 列名智能匹配 — 长词优先策略严谨，四种期初分档格式识别覆盖完整

- 主题系统和卡片控件 — 均无问题

### 2025-06-09：全量代码复核 — 发现并修复 3 个致命问题

在功能开发全部完成后，对 12 个源文件做了一轮逐行审查。配合代码审查、系统调试、完成前验证等多项检查流程交叉比对。审查中发现了下面 3 个问题并当场修掉：

#### 🚨 问题一：先进先出引擎的数组越界

**位置**：核心逻辑 → 先进先出引擎 → 期初分档填充阶段

**现象**：当期初余额表的账龄分档列数量比当前设置的分档数量多时（比如期初表有 6 个分档列，但步骤 2 只设了 3 个区间），程序会直接崩溃，报数组下标超出范围的错误。

**根因**：引擎在遍历期初分档时，用期初分档的下标直接去取当前分档的区间定义，没有检查下标是否越界。

**修法**：遍历期初分档的每一步都先判断下标是否在当前分档范围内。如果超出了，改用「下标序号乘以 365 加上偏移天数」的方式粗略推算这笔余额应该落在哪个分档，不再直接取值。

#### ⚠️ 问题二：增删分档时别名列表没同步

**位置**：界面 → 步骤 2 → 新增分档和删除分档按钮

**现象**：给每个分档填好了自定义别名（比如「3 个月内」「4 到 12 月」），然后点新增分档加了一行——新行的别名是空的，这没问题。但如果点了删除中间一行，后面的所有别名字符串会集体往前挪一位，导致每个别名和它的分档天数对不齐。导出的 Excel 表头跟着就全乱了。

**根因**：新增和删除分档时只更新了分档天数列表，忘了同步更新别名列表。两个列表各自独立维护，删掉中间一个元素后列表长度和对应关系全部打乱。

**修法**：新增分档时同步追加一个空字符串进别名列表；删除分档时同步删除别名列表中对应下标的元素。同时把「从界面读取别名」的逻辑改成和「从界面读取天数」完全一致的过滤规则——遇到填了非法天数的行，两边一起跳过，确保列表永远一一对应。

#### 🚨 问题三：后台线程直接操作界面控件

**位置**：界面 → 步骤 3 → 计算日志输出

**现象**：计算在后台线程跑着（为了不卡界面），但往屏幕上写日志的时候，后台线程直接调了界面控件的方法。这会导致什么后果不固定——有时候正常，有时候界面卡住不动，有时候整个窗口直接闪退。全看操作系统当时怎么调度线程。

**根因**：图形界面框架不允许非主线程操作控件。所有界面更新——改文字、变颜色、插内容——都必须由主线程来执行。后台线程直接操作等于闯红灯。

**修法**：把所有界面操作包进一个函数，通过框架提供的调度方法扔给主线程排队执行。后台线程只负责「安排任务」，不亲自碰界面。日志还是实时显示，但安全了。

- 数据加载与清洗 — 空值填充和类型转换逻辑正确

## 🙋 常见疑问

**问：我好几年的序时账要一起算，怎么喂进去？**

答：当前一次只能选择一个序时账文件，也不会自动合并多个 Sheet。请先在 Excel 中把需要的期间整理到一个工作表，再在步骤 1 手动选择该 Sheet。

**问：我每年都要做账龄分析，能不能把去年的结果直接当今年期初用？**

答：能。去年导出底稿后，把期末各分档填到今年的期初表里（列名用 `0-90天` 这种格式），步骤 1 载入后程序会自动识别这些分档列并切到分档模式，步骤 2 再填好期初日期。工具会自动把去年的账龄「老化」后加上今年的发生额，得到最新的账龄结构。

**问：应收和应付的科目可以一起算吗？**

答：可以。先确认名称合并和暂估归属，程序自动把反向余额转入对应的成对科目并计算账龄，再完成同一单位成对对抵。最终只有一套账龄，资产与负债分别列示。

**问：红字冲减（负数发生额）能处理吗？**

答：能。引擎内部会自动把正负数求净额，负数不参与正向追溯，余额公式自动抵消。已用专门的测试用例验证过。

**问：输出的分档表头可以自己起名字吗？**

答：能。在步骤 2 的“账龄名称”列填写即可。名称不能为空、不能重复；默认名称会随上下限自动更新，手工改名后会保留，导出表头与界面完全一致。
